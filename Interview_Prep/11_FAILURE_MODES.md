# 11 — Failure Modes, Consistency & Recovery

Every claim in this file is checked against `amplify/functions/section-changes/handler.ts`, `amplify/functions/find-slots/handler.ts`, `amplify/functions/shared/attendance.ts`, `amplify/functions/parse-timetable/`, `amplify/functions/import-data/`, and `amplify/data/resource.ts`. Where the code doesn't handle something, that's stated plainly, not smoothed over.

---

## 1. Failure-mode table

| # | Scenario | What Slate does today | Severity | Correct design |
|---|---|---|---|---|
| 1 | **Two CRs claim the same section in a race** | `claimCr` checks `!resource.hasCr` inside the Cedar decision (`sectionEntity` reads the *current* `ClassRep` scan result at request time), then does an unconditional `PutCommand` with a fresh `randomUUID()` — no conditional write, no `ConditionExpression` on the `ClassRep` table. Two near-simultaneous `claimCr` calls could both pass the Cedar check (both scans happen before either write lands) and both succeed, creating two `ClassRep` rows for the same `sectionKey` | 🟠 Real gap | A `ConditionExpression: attribute_not_exists(sectionKey)` (using `sectionKey` as the table's primary key, not `id`) would make the second write fail atomically instead of relying on a read-then-write race |
| 2 | **Concurrent CR edits to the same course** (two CRs of different sections of the same course try to cancel or add at once) | Each write is independent per `ScheduleChange` row; `cancelRows`/`extraRows` write via `BatchWriteCommand` (25 at a time). `assertNotCancelled` does a fresh scan-and-check immediately before writing, but there's a window between that check and the write where a second concurrent request could pass the same check | 🟠 Real gap, rare in practice (one CR per course-in-batch acts, and it needs two people racing to the same course within milliseconds) | A conditional check tied to `groupId`/`relatedSlotId` uniqueness at write time, not just a pre-write scan |
| 3 | **`BatchWriteCommand` partial failure** | `writeRows()` chunks rows into groups of 25 (DynamoDB's batch-write limit) and calls `BatchWriteCommand` per chunk, but **never inspects `UnprocessedItems`** in the response. DynamoDB batch writes can partially fail under throttling and silently return the unwritten items in that field | 🔴 **Silent data loss.** A cancel or extra-class action that writes rows for, say, three sections could land for two and silently drop the third — the caller sees success (`{ cancelled: rows.map(...) }` returns the *intended* rows, not what was confirmed written) | Retry `UnprocessedItems` with backoff; at minimum log when it's non-empty |
| 4 | **A `moveOccurrence` fails after writing `MOVED_FROM` but before `MOVED_TO`** | `writeRows([...from, ...to])` is one call site but internally chunks into 25-row batches with no transaction wrapping the whole set — if the process is killed or throws between chunks, a class could be recorded as cancelled (`MOVED_FROM`) with no corresponding `MOVED_TO` row ever written | 🟠 | Both halves share a `groupId`, so a consistency-check pass (`find all groupId with a MOVED_FROM row and no matching MOVED_TO`) is possible after the fact, but nothing runs it today |
| 5 | **Undo on a partially-affected change** | `undoChange` correctly scopes to the caller: the maker can undo the whole `groupId`, or a CR can undo only their own section's rows within that group (`targets = rows.filter((r) => keyOf(r) === key)`). This is a genuinely well-handled case — the group can end up in a legitimate "partially undone" state (`live()` per row, not per group), and both `StudentDashboard` and the admin activity view are expected to render that correctly since `ScheduleChange` rows are read independently | 🟢 Handled by design | — |
| 6 | **Cognito `AdminGetUserCommand` fails or the user has no verified email** | `emailOf()` sets the cached value to `''` when `email_verified !== 'true'`, and doesn't otherwise catch a thrown SDK error. An AWS-side Cognito outage or throttling on `AdminGetUserCommand` would throw out of `emailOf`, which is called unconditionally at the top of the handler (`const email = await emailOf(event.identity)`) — every field, including read-only `mySection`, fails outright rather than degrading | 🟠 | A degraded "we couldn't verify your identity right now" response distinct from "you have no section" would be more honest than a generic 500 |
| 7 | **A student's email doesn't resolve to any section** (`resolve()` / `homeOf()` returns `null`) | Handled explicitly and well: `mySection` returns `JSON.stringify(null)`, `batchRoster` returns `null`, and `claimCr` throws a specific, actionable message ("Your section couldn't be found from your roll number, so you can't claim CR yet.") This is the one failure mode `docs/TESTING.md` explicitly documents having hit and fixed in production ("your roll number isn't in the uploaded lists") | 🟢 Handled, and known to have happened for real | — |
| 8 | **Two students with the same roll number but different prefixes** (`IIT2024001` vs `IIB2024001`) | Explicitly designed for: `StudentSection.rollPrefix` disambiguates, and `homeOf()`'s `ok()` check matches on `rollPrefix` when present, falling back to `branch` for legacy rows without one. Git history (`df33b1a Keep the roll prefix: IIB2024001 and IIT2024001 are two people`) shows this was a real bug that was found and fixed, not a hypothetical | 🟢 Fixed, with a commit as evidence | — |
| 9 | **A CR revoked while a change is in flight** (admin deletes the `ClassRep` row between the Cedar check and the write) | The Cedar check reads `ctx.reps` from a scan taken once, at the top of `context()`, for the whole request; there is no re-check immediately before `writeRows`. A revocation landing in that window would let an already-in-flight, now-invalid CR action complete | 🟢 Low impact — the write itself is still correctly attributed (`changedBy`, `changedBySection`) and remains auditable/undoable by an admin afterward; this is a narrow timing window with a recoverable consequence, not silent corruption | Re-check authorization immediately before the write, not just once per request, if this needed hardening |
| 10 | **A course taught by a different professor per section, and an Extra is added for the wrong professor's classes** | Deliberately guarded: `addExtra` filters `courseRows` down to only the sections sharing the CR's own professor before computing `courseEntity`/authorizing (`const profs = new Set(courseRows.filter((r) => keyOf(r) === keyOf(ctx.mine!) && r.faculty).map(...))`). `docs/TESTING.md` check #11 explicitly tests this ("IVP → pre-selects B2 and C, not A") | 🟢 Handled, and covered by the manual test checklist | — |
| 11 | **`extraSections` is asked to include a section the professor doesn't teach** | Explicitly rejected with a clear error: `Only sections your professor teaches for this course can be included (${all.join(", ")})` — the server never trusts a client-supplied section list beyond validating it's a subset of the server-computed one | 🟢 Handled | — |
| 12 | **Ingestion: a timetable sheet the reader can't parse reliably** (merged cells, mixed programs, section-less electives) | `parse-timetable/reader.ts` is explicitly designed to flag rather than guess: `README.md` states "nothing that fails a check is guessed; it's listed for the admin," and `AdminUpload.tsx`'s two-step flow (parse → review issues → confirm import) exists precisely because ingestion accuracy on real, inconsistent institutional sheets is not assumed to be 100% | 🟢 Handled by process, not by perfect code | Textract/Bedrock normalization was planned (`AWS_GUIDE.md` Part 5) but never reached production — `CREDITS.md` and `README.md` both say plainly that Bedrock model-access quota blocked it, and the deterministic reader plus admin review is what actually shipped |
| 13 | **`import-data` runs twice on the same sheet, or is interrupted mid-write** | `importData`'s `dryRun` flag lets an admin preview before committing, and the code diffs against existing DynamoDB rows before writing (per `resource.ts`'s comment: "diffs against DynamoDB and (unless `dryRun`) writes the changes"). There's no transaction wrapping the whole import — a crash mid-write leaves a partial import, discoverable only by re-running the parse/diff step and seeing what's still "new" | 🟠 Recoverable, but not atomic | A consistency-check re-run is the actual recovery path today (diff-and-reapply), which is workable for an admin-only, infrequent, per-semester operation |
| 14 | **`Enrollment` rows reference a `courseId` that no longer exists in `TimetableSlot`** (e.g. a course removed by a later import) | Nothing in `attended()` (`shared/attendance.ts`) validates that an `ADD`/`DROP` `courseId` still has matching `TimetableSlot` rows — a stale `Enrollment` row simply matches nothing and is silently a no-op (`for (const e of adds) for (const r of slots) if (r.courseId === e.courseId ...)` — if no `r` matches, nothing is added, no error) | 🟡 Silent but harmless — degrades to "enrollment has no effect" rather than corrupting data | An admin-facing "orphaned enrollment" report would surface this; today it's invisible |
| 15 | **A student views a week where an elective's registration data hasn't been uploaded yet** | Explicitly designed for, not a bug: `attended()`'s `electivesUnconfirmed` flag is true whenever no `Enrollment` ADD exists for any elective in the batch, and the whole basket is shown instead of guessing which elective the student takes — `CLAUDE.md` §2 states this is intentional ("without registration data the whole basket shows, labelled as such") | 🟢 Handled by design | — |
| 16 | **`find-slots` is asked about a course that no section in the given groups actually teaches** | `courseRows` filters to `slots.filter(r => inBatch(r, batch) && r.courseId === a.courseId && r.section !== '*')`; if empty, `addExtra` throws a specific error (`${a.courseId} isn't taught in ${batchKey(batch)}`). `find-slots` itself doesn't have the identical guard — an empty `professors` array and empty irregular set simply means the finder falls back to pure section-availability, which is a reasonable (if silent) degradation rather than an error | 🟡 Inconsistent between the two Lambdas — one throws, one degrades quietly | Align: either both should throw on an unknown course, or both should degrade the same documented way |
| 17 | **CloudWatch/Cedar-decision logging itself fails or is throttled** | `authorize()` logs the decision via `console.log(JSON.stringify(...))` unconditionally, before checking `decision !== 'allow'` — the log line and the authorization decision are not coupled to any external system that could fail independently; a `console.log` failure isn't a realistic Lambda failure mode, so this is low-risk by construction | 🟢 | — |
| 18 | **A change's `expiresAt` TTL sweep hasn't run yet, but the app's own date filtering has moved on** | `find-slots` and `section-changes` both filter `ScheduleChange` rows by `date` in application code after scanning (`live = changes.filter(...)`), independent of whether DynamoDB has actually deleted the expired row yet (TTL deletion is asynchronous and can lag by up to ~48 hours per AWS's documented behavior). This means correctness never depends on TTL timing — TTL is purely a storage-cost control, not a correctness mechanism | 🟢 Good design: TTL failure/delay degrades to "the table is a bit bigger than expected," never to "students see stale changes" | — |

## 2. Data consistency between `ScheduleChange` rows for the same `groupId`

This is the schema's central integrity question, since `docs/PLAN.md` explicitly redesigned `ScheduleChange` around "one row per affected section" specifically to keep per-section queries simple in `StudentDashboard`. That design trades write-side atomicity for read-side simplicity, and it's worth being precise about what that trade actually costs:

**What ties rows together:** `groupId` (shared by every row from one action) and, for a move, `kind` distinguishing `MOVED_FROM` from `MOVED_TO`. Nothing in the schema enforces that a `groupId`'s rows are complete or consistent — there's no aggregate/parent record, by design (`ScheduleChange` has no groupId-keyed parent row).

**What can actually go wrong, concretely:**
- A `moveOccurrence` that fails between writing the `from` rows and the `to` rows (see #4 above) leaves a `groupId` with only `MOVED_FROM` entries — a class shows as cancelled everywhere, with no replacement, and nothing surfaces this as broken. A student sees "cancelled by X" and that's a *coherent*, if incomplete, story — it just isn't the one that actually happened.
- A `BatchWriteCommand` silently dropping `UnprocessedItems` (see #3) could leave a `groupId` where, say, section A and B got their row but section C didn't — section C's students would never see the change at all, with no error anywhere in the system.
- `undoChange`'s per-section undo (case #5) is the one place partial-group states are *expected and correct* — it's the only intentional exception to "a groupId's rows should all agree."

**Why this wasn't hardened further:** at hackathon scale, with a single CR acting synchronously through one Lambda invocation per action, the actual probability of hitting the batch-write partial-failure path is low, and it was never observed in testing (`docs/TESTING.md`'s checklist walks the happy path and the permission-denial path, not injected write failures). The honest answer here is "this is a real gap, the failure modes are understood, and the reason it wasn't fixed is that DynamoDB transactions (`TransactWriteCommand`, which supports up to 100 items atomically) would have been a small, correct fix that simply wasn't prioritized over shipping the CR/finder/feed flow within four days."

## 3. What a judge or interviewer would actually ask, and the honest answer to each

**"What happens if two CRs try to claim the same section at the same instant?"**
→ There's a real race: the check and the write aren't atomic. It's `ConditionExpression: attribute_not_exists(sectionKey)` away from being fixed, and I know that because I traced the exact code path rather than assuming Cedar's `permit`/`when` check was itself atomic — it isn't; it's a policy decision over a stale scan.

**"What happens if a Lambda dies halfway through a multi-section change?"**
→ `BatchWriteCommand`'s `UnprocessedItems` isn't checked, so a partial write is possible and would currently be silent. That's the single biggest concrete gap in this document, and the fix is small (either check `UnprocessedItems` and retry, or move to `TransactWriteCommand` for anything under 100 items, which every real action here is).

**"How do you know the ingestion pipeline didn't just silently write wrong data?"**
→ It doesn't guess: unparseable sheets are flagged for the admin, not defaulted. The two-step upload flow (parse → review → confirm) exists specifically so a human checks the diff before anything lands in DynamoDB. This is a process guarantee, not a code guarantee, and that's a deliberate, stated trade-off (`README.md`'s "honest call on ingestion" section says as much).

**"What's the one thing you'd fix first if this had to be reliable?"**
→ `BatchWriteCommand`'s dropped `UnprocessedItems`, because it's the one failure mode that's both realistic (DynamoDB throttling under load is a documented, common occurrence) and completely silent today — the caller gets a success response regardless.
