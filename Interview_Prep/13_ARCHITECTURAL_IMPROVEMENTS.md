# 13 — Architectural Improvements

Everything here is scoped against `CLAUDE.md` §2's explicit non-goals and `docs/PLAN.md`'s "later" phase, so it's clear which cuts were deliberate hackathon-scoping decisions (made in writing, before the code that would've needed them) rather than things nobody thought of. Where a decision was made *and reversed* mid-build (the professor-login pivot), that's called out separately since it's a stronger interview story than a clean non-goal.

---

## 1. Professor logins — a cut that was made twice, for different reasons

`CLAUDE.md` §2's "Revision note (Day 3 → 4)" documents an actual pivot: the product started faculty-driven (a professor schedules, students see it — this is still visible in the old `README.md`'s table describing a "Schedule a session" screen for Faculty and a Cedar `FACULTY` group, and in `TEST_ACCOUNTS.md`'s still-present `test-faculty@iiita.ac.in` account and FACULTY-group instructions) and was rebuilt around a **student CR model** instead, because that's how changes actually happen at IIITA: the professor tells the CR, the CR tells the class. This isn't a corner cut for time — it's a correction to match reality, made after building the faculty version first and recognizing it modeled the wrong actor.

**What real professor accounts would add, with more time:**
- A read-only professor view of their own week across every section/batch they teach (the data already exists — `TimetableSlot.faculty` — this is a query, not a schema change) so a professor could self-serve "am I free Thursday" instead of a CR having to ask via the finder.
- A "confirm" step where the professor acknowledges a CR-proposed change before it's final, which would need a real approval flow — explicitly ruled out by `CLAUDE.md`'s non-goals ("voting or approval flows between students/CRs... one CR decides"). Reintroducing this changes the trust model from "CR self-serves and is accountable via the audit log" to "every change needs sign-off," which is a real product decision, not just more code — worth naming as a genuine trade-off rather than a strict improvement.
- Professor-initiated changes bypassing the CR entirely — the more natural long-term shape, but it needs real professor onboarding (accounts, verified identity, mapping a Cognito user to a `faculty` string that today is just free text extracted from spreadsheet legends) that never existed even in the faculty-driven prototype; `test-faculty@iiita.ac.in` was a stand-in account with FACULTY group membership, not a real onboarding flow.

## 2. Recurring changes — an explicit non-goal, held to consistently

`CLAUDE.md` §2: "Recurring changes (every change is one date)." Every `ScheduleChange` row is single-dated by schema design (`date: a.string().required()`), and the whole product concept — "this week and next week only," TTL-expired rows — depends on changes being one-shot. This wasn't a corner cut so much as a scope boundary that shaped the entire data model; reversing it later is not a small patch.

**What it would take:** a `RecurringChange` concept (e.g. "IML cancelled every Thursday until further notice") that materializes into dated `ScheduleChange` rows on read or on a scheduled job, rather than being stored as N individual rows. The clean way to add this without breaking the current one-row-per-section-per-date model: a separate table with a start date, an optional end date, and a weekday, whose rows get expanded into the existing `ScheduleChange` shape by a small Lambda (materialized view pattern) — this keeps `StudentDashboard`, the feed, and the finder completely unaware recurring changes exist, which is the right boundary if this were added later.

## 3. Real notification (SES) — planned, then explicitly dropped

The architecture table in `CLAUDE.md` §3 has a line that reads, plainly: "Notification | In-app 'What changed' feed (SES dropped)." This one is worth being precise about because it's a genuine reversal with a real reason, not silence: `AWS_GUIDE.md` Part 8 documents a real SES plan (sandbox-mode email to verified addresses only, a `SendEmail` call on a status-flip trigger), written when the product was still faculty-driven and "Confirm & Notify" was a screen. When the product pivoted to the CR model and per-date `ScheduleChange` rows with an in-app feed, a push/pull notification via email became redundant with the feed for the demo's scope, and SES's sandbox-mode restriction (only pre-verified recipient addresses) made it useless for showing real student notification on camera anyway — you can't email a whole section of real students from an unverified sandbox account. Dropping it was the right call given the constraint, not a shortfall.

**What real notification would add:** SES (or, more realistically today, an Amplify-native push via a mobile client, which doesn't exist — see §6) sending an actual email/push the moment a `ScheduleChange` row is written, rather than relying on students to open the app and check "What changed." This is the single most-requested-feeling missing piece for a product meant to replace a WhatsApp poll — the whole point of the WhatsApp flow being annoying is that it pushes to you; the current design pulls. The honest fix: an SES production-access request (a real approval process, not a code change) plus a small Lambda subscribed to `ScheduleChange` writes (DynamoDB Streams → Lambda → SES), which is additive and doesn't touch the existing write path at all.

## 4. Better ingestion — the one area where the plan and the ship diverged most visibly

`README.md`'s "How the timetable reading works, honestly" section is the most candid document in the repo: Textract + Bedrock was the actual plan (`AWS_GUIDE.md` Part 5's "gate test" methodology — try Textract on a real PDF, decide automated vs. hand-structured, *before* building anything else), but on the team's AWS account "every Bedrock model's daily token quota was 0, and that quota can't be raised from the console" — an infrastructure blocker outside the team's control, hit and documented rather than hidden. `slate/scripts/bedrock-normalize-timetable.py` exists in the repo as the code that was written for this path and never got to run against real data in production. What shipped instead — a deterministic `.xlsx`/`.csv` reader (`parse-timetable/reader.ts`) that cross-checks its own merged-cell interpretation against each course's declared L-T-P-S hours, with the admin reviewing a diff before anything writes — is a legitimately good fallback, not just "the thing that was left over." It's arguably more trustworthy for a hackathon demo than an LLM-normalization pass whose accuracy was never validated on the real, messy sheets, since the deterministic reader's failures are visible (flagged for the admin) rather than silently plausible-looking wrong output the way an LLM's could be.

**What real ingestion improvements would look like, with time and quota:**
1. Actually run Textract + Bedrock against the real AAA PDFs once quota exists, and — critically — validate its output against the same real course-list cross-checks the deterministic reader already does, rather than trusting it blindly. The deterministic reader's validation logic is the right foundation to keep even if the extraction step changes.
2. Handle the sheets the current reader explicitly can't (`README.md`: "sheets that mix several programs, and electives with no section, aren't imported automatically") — this is a known, named, current gap, not hypothetical.
3. PDF support at all — today's pipeline reads `.xlsx`/`.csv` only; the real AAA source documents are frequently PDFs, and `README.md` states plainly "PDFs aren't supported yet."

## 5. What CLAUDE.md ruled out and why each one was the right call for four days

Quoting `CLAUDE.md` §2 "Non-goals" directly and evaluating each:

- **Voting/approval flows between students/CRs** — correctly cut. This is the feature most likely to balloon scope (who has quorum, what happens on a tie, notification-of-vote) for a problem that doesn't need consensus: one CR per course-in-batch, accountable via the audit log, is a simpler and arguably better-fitting model for how changes actually happen (a professor tells one person, not a committee).
- **Chat/messaging** — correctly cut. Slate's entire value proposition is *replacing* the WhatsApp thread with structured data; building a worse chat feature inside the app would have undermined the pitch, not supported it.
- **Professor logins** — see §1. Cut, reversed from an earlier build, for a real product reason.
- **Recurring changes** — see §2. Cut, and the whole data model was shaped around the cut (dated rows, TTL) rather than the cut being bolted onto a design that assumed recurrence.
- **Crowdsourced edits to regular timetable data** — correctly cut. Regular `TimetableSlot` data being admin-only, with `ScheduleChange` as the only student/CR-writable surface, is what makes the Cedar policy tractable (`resource.crs` is computed from immutable `TimetableSlot` rows the server trusts) — if students could edit the base timetable, every authorization decision would need to account for a moving target.
- **User-created groups** — correctly cut, and philosophically central: `CLAUDE.md` §0 states this idea was chosen specifically *because* "it needs no second user to already exist — the sections it coordinates are real, pre-existing enrollment groups, not a community anyone has to build." Adding user-created groups would contradict the reason this idea was picked over the two abandoned predecessors.
- **A native mobile app** — correctly cut for four days; Amplify Hosting + a responsive web app gets a public URL same-day, which a mobile app build/release pipeline could not have.
- **Multi-institution support** — correctly cut; "IIITA is hardcoded" is honest and appropriate, and generalizing this (see §10 §5 of the performance doc) is real, non-trivial schema work that would have been premature without a second institute's real data to design against.
- **Visual/UI design work until flows are done** — correctly sequenced, and git history bears this out: the early commits (`e0f4f06` onward through the CR pivot) are functionality-first, with the visible design pass (`80ebb58 Redesign: the printed timetable, made live`, the font/theme commits) landing after the core flows worked, not before.

## 6. Beyond CLAUDE.md's explicit list: real architectural debt worth naming unprompted

- **The registration-driven data model in `docs/DATA-MODEL.md` was designed but never migrated to.** This document is the single clearest piece of evidence that the team understood their own schema's limits: it names the exact problems (electives, minors, drop-year students, courses shared across programs) that the current section-based model handles with special-case logic (`Enrollment` ADD/DROP exceptions, `RollRange` fallback, the `blocks()`/`heldFor()` section-arithmetic helpers scattered through `attendance.ts` and `find-slots/handler.ts`) rather than a clean primitive. The plan replaces "attends your home section, adjusted by exceptions" with "attends exactly what you're registered for" — which the team correctly identified would delete most of the special-case code, not add to it. This is the strongest "what I'd do differently" answer available: not a new feature, but the removal of accumulated section-arithmetic complexity in favor of a data model that matches reality (the institute's own mid-sem examinee list is literally a registration table).
- **The scan-everything DynamoDB access pattern** (§10 of this series) — known, sized correctly for today, with the fix already sketched in `docs/DATA-MODEL.md`'s "Access patterns" section but not implemented.
- **`BatchWriteCommand`'s `UnprocessedItems` never checked** (§11 of this series) — small, concrete, and the single highest-value silent-failure fix available.
